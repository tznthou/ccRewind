# 為什麼會出現「孤兒 subagent 記錄」

> 本文說明 ccRewind v1.21.0 及之前版本存在的一個索引狀態問題：為什麼會有大量 subagent 記錄指向已經不存在的檔案，卻仍然被標記為活躍。修正已合併至主線，將於下一個版本發布。

## 現象

在一份使用了約五個月的真實索引庫裡，1,574 筆 subagent 記錄中有 **1,369 筆（87%）** 指向磁碟上已經不存在的檔案，而且每一筆都還標記為活躍狀態。

這不是隨機的資料損壞。把記錄按對話開始日期攤開來看，界線乾淨得像刀切：

| 對話日期 | 檔案已消失 | 檔案還在 |
|---|---|---|
| 2026-06-30 | 4 | 0 |
| 2026-07-01 | 1 | 0 |
| 2026-07-02 | 5 | 0 |
| 2026-07-03 | 0 | 2 |
| 2026-07-04 | 0 | 3 |

沒有任何一天是混合的。這條界線精確落在檢查當日的 30 天前。

## 原因：兩個獨立機制交會出來的缺口

### 一、Claude Code 會自動刪除超過保留期的對話記錄

Claude Code 把每段對話存成 `~/.claude/projects/<專案>/<sessionId>.jsonl`，並且有保留期限機制（設定項 `cleanupPeriodDays`，預設 30 天）。超過期限的檔案會被自動刪除。

上面那條 30 天界線就是這個機制留下的痕跡。沒有調整過設定的使用者，行為都一樣。

**這一點很關鍵：檔案消失不是異常，是每天都在發生的正常狀況。**

### 二、subagent 的記錄是獨立檔案，掛在 parent session 目錄底下

subagent（透過 Task／Agent 工具啟動的子代理）不是寫在主對話檔裡的某個欄位，而是各自獨立的檔案：

```text
~/.claude/projects/<專案>/
├── <sessionId>.jsonl              ← 主對話
└── <sessionId>/
    └── subagents/
        └── <agentId>.jsonl        ← subagent 對話，各自獨立
```

注意 subagent 目錄的名字取自 parent session 的 ID。主對話檔和 subagent 目錄是**兩個獨立的檔案系統項目**，但在 ccRewind 的掃描邏輯裡，後者要透過前者才找得到。

### 三、ccRewind 的兩套清理機制，只有一套不依賴「掃得到」

ccRewind 是唯讀的觀察者，每次啟動掃描 `~/.claude/`，比對磁碟現況與索引庫。清理「磁碟上已經沒有了」的記錄有兩條路徑，而它們的設計差異就是這個問題的根源：

**主對話走集合減法**

```text
archiveStaleSessionsExcept(這次掃到的所有 session id)
```

它的判斷基礎是「**不在**掃描結果裡」。一個 session 的檔案消失了，它自然就不在集合中，於是被標記。**這條路徑不需要掃描到那個 session 就能處理它** —— 這正是它可靠的原因。

**subagent 走巢狀迴圈**

```text
for (掃描到的每個 project)
  for (掃描到的每個 session)          ← 問題在這一層
    掃描這個 session 的 subagents/
    比對、清理
```

subagent 的清理巢狀在「磁碟上還掃得到的 session」迴圈裡面。要處理某個 subagent，前提是**先掃描到它的 parent session**。

於是因果鏈接上了：

1. parent session 的 `.jsonl` 被保留期限機制刪除
2. 下次掃描找不到這個 session，外層迴圈根本不會進入
3. 它底下的 subagent 記錄永遠不會被檢查到
4. 而 subagent 又被主對話那條兜底路徑明確排除在外（`EXCLUDE_SUBAGENTS`）

**兩邊都不管，記錄就永久卡在活躍狀態。**

這是典型的責任邊界漏接：主對話的清理說「subagent 不歸我管，交給 subagent 掃描段」，而 subagent 掃描段只在特定條件下才會被執行到 —— 偏偏那個條件（parent 還在）正是問題發生時第一個不成立的。

## 為什麼會累積到 87%

因為這不是一次性事件，是每天都在發生的持續累積。

每過一天，就有一批滿保留期限的對話被刪除，它們的 subagent 記錄隨即變成孤兒，而且**永遠不會被修正**。使用時間越長，孤兒佔比越高——只有保留期限內的 subagent 記錄是正確的，之前的全部是孤兒。

五個月的使用累積出 87%，就是這樣來的。這個比例會隨使用時間持續上升，不會自己回頭。

## 影響

**內容沒有遺失。** 這些對話的訊息都還完整存在索引庫裡，只是「狀態標記」與磁碟現況不符。

**狀態自相矛盾。** 那 1,369 筆孤兒的 parent session，經查證**全部**都已被兜底機制正確標記為封存。也就是說，同一段對話的兩半——主對話標記為已封存，它的 subagent 標記為活躍——狀態彼此打架。

**專案統計被灌水。** 專案統計的查詢只過濾封存狀態，並未排除 subagent：

```sql
SELECT s.project_id, COUNT(*) AS session_count, ...
FROM sessions s ... WHERE s.archived = 0
```

實測同一份索引庫，這個查詢在修正後回報 **389 筆**活躍記錄（184 筆主對話 + 205 筆 subagent）。而那 1,369 筆幽靈 subagent 在修正前同樣落在 `archived = 0` 底下、被同一個 `COUNT` 算進去——**灌進來的量是修正後全部真實記錄的 3.5 倍**。

**但每日趨勢圖在預設設定下不受影響。** 這一點值得單獨說明，因為它解釋了問題為何能潛伏這麼久。趨勢圖的查詢帶有時間視窗，預設 30 天：

```sql
... WHERE started_at IS NOT NULL AND archived = 0
    AND started_at >= date('now', '-30 days')
```

而孤兒記錄依定義全部落在保留期限之外（那正是它們的檔案被刪除的原因）。趨勢圖這個 30 天是 ccRewind 自己的查詢視窗，與 `cleanupPeriodDays` 無關——**只是在雙方都用預設值時恰好對齊**，時間視窗於是把所有幽靈記錄擋在外面。實測修正前後都是 389 筆，分毫不差。

這個巧合有兩個方向會被打破，而且都不難遇到。一是儀表板的時間範圍本來就可以切成 90 天或「全部」，切下去視窗就攔不住了——選「全部」時查詢根本不加時間條件，1,369 筆全部灌進來。二是把 `cleanupPeriodDays` 設得比視窗短，那段「檔案已被刪除、卻仍落在視窗內」的區間同樣會混進圖裡。反過來把保留期限設得比 30 天長則不影響，孤兒只會離視窗更遠。

**最常被看的那張圖，偏偏就是預設值下擋得住的那一個。** 這類「被另一個條件恰好遮住」的缺陷特別難靠日常使用發現——只有直接去比對索引庫與磁碟現況，它才會現形。

## 修法：標記封存，而不是刪除

修正的方向是給 subagent 補上一條與主對話同級、不依賴「掃得到 parent」的清理路徑。

值得說明的是為什麼選擇**標記封存（archive）而非刪除**：

ccRewind 對 `~/.claude/` 是純唯讀的觀察者。當那邊的檔案被保留期限機制刪除後，**索引庫裡的副本就成了那段對話唯一還存在的地方**——這正是一個對話考古工具最不可替代的價值。自動硬刪等於主動銷毀使用者再也拿不回來的東西。

要清理是儲存空間管理的職責，那是使用者主動的決定，性質完全不同。

封存也設計成可逆的：如果檔案之後被還原（`rsync -a`、Time Machine 還原都會保留原始 mtime），下次掃描會自動解除封存標記。這一點特別容易被忽略——如果增量比對只看檔案修改時間，還原一個 mtime 沒變的檔案會被直接跳過，封存標記就再也解不開了。

## 這會發生在誰身上

在 **v1.21.0 及之前的版本**，只要同時滿足兩個條件：

1. 使用 ccRewind 索引的時間超過 `cleanupPeriodDays`（預設 30 天）
2. 這段期間用過 subagent

就**必然**會累積孤兒記錄。這不是機率問題，是時間到了就會發生。規模與使用強度成正比。

換句話說，這不是邊緣案例，而是每一位長期使用者都會遇到的必然狀況——這也是為什麼它值得一篇說明，而不只是一行 changelog。修正合併之後，既有的孤兒記錄會在下一次索引時被補正為封存狀態，不需要重建索引庫。
